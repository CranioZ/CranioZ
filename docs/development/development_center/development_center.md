# CranioZ Development Center

## 1. Overview

The **CranioZ Development Center** is an independent desktop application designed to centralize development and maintenance workflows for the CranioZ project.

It provides a unified interface for source code extraction, code verification, automated testing, architecture inspection, documentation generation, application builds, and installer creation.

The application integrates existing development tools and project scripts rather than replacing their underlying functionality.

### 1.1 Goals

- Centralize development workflows in a single application.
- Reuse existing code extraction and packaging utilities.
- Automate code verification and testing.
- Generate and validate project documentation.
- Build executable applications and installers.
- Provide consolidated reports and execution history.
- Reduce repetitive terminal operations.

### 1.2 Scope

The Development Center is a development utility, not a clinical CranioZ module.

It must operate independently of the CranioZ application runtime, allowing development and maintenance tasks to continue even when the main application cannot start.

## 2. Application Structure

The application is organized into seven functional areas.

### 2.1 Dashboard

Provides an overview of the project's development status.

Features:

- Last verification results.
- Test execution status.
- Code quality and type-checking results.
- Test coverage.
- Documentation build status.
- Last successful application build.
- Recent execution history.

The dashboard presents information generated by the other application areas. It should not independently execute development operations.

### 2.2 Code Extraction

Provides tools for extracting and consolidating project source code.

Features:

- Select individual files or directories.
- Extract specific modules or architectural layers.
- Generate a consolidated `.txt` file.
- Save reusable selection profiles.
- Configure exclusion rules.
- Configure output filename and destination.

Supported selection profiles may include:

- Full Project.
- Core Architecture.
- Domain Layer.
- Application Layer.
- Infrastructure Layer.
- UI Layer.
- Specific Module.
- Documentation Only.

#### TXT Export

The generated text file should:

- Preserve the relative path of each source file.
- Include the original filename and extension.
- Separate files using clear delimiters.
- Optionally include a project directory index.
- Preserve the original source content.

Common exclusions include:

- `.venv/`
- `__pycache__/`
- `.git/`
- Build and distribution directories.
- Cache directories.
- Binary and generated files.
- Environment files and credentials.
- Private keys, certificates, and access tokens.
- Clinical data and patient records.
- Logs containing potentially sensitive information.
- Local configuration and user-data directories.

Sensitive files must be excluded by default. Explicit inclusion should require a clear warning and user confirmation.

The extraction process must not modify the original project files.

**ZIP export and general-purpose archive generation are outside the scope of this application.**

### 2.3 Verification & Testing

Centralizes code quality checks, static analysis, and automated testing.

#### Code Verification

Integrate the project's existing tools:

- Ruff — linting and code formatting.
- Mypy — static type checking.
- Import Linter — architectural dependency contracts.
- Dependency auditing — identification of known vulnerable dependencies.

Verification operations should distinguish between diagnostic execution and operations that modify source files.

The application must reuse the project's existing configurations and avoid maintaining duplicate verification rules.

#### Testing

Integrate:

- Pytest — automated test execution.
- Coverage.py — test coverage measurement.

Features:

- Run the complete test suite.
- Run selected tests.
- Run tests by module or architectural layer.
- Display test failures and execution output.
- Display coverage results.
- Maintain execution history.

The application must use the project's existing test configuration.

### 2.4 Documentation

Provides tools for generating, validating, and publishing project documentation.

Documentation is organized into three categories:

#### API Documentation

Documents the public interfaces of the application.

Features:

- Extract classes, functions, methods, and signatures.
- Document parameters and return types.
- Process type annotations.
- Extract and render docstrings.
- Generate navigable API references.

Type annotations provide structural information but do not replace docstrings or descriptions of implementation behavior.

#### Technical Documentation

Documents the software architecture and development processes.

Content includes:

- Architecture and design decisions.
- Module responsibilities.
- System workflows.
- Technical specifications.
- Developer guides.

Markdown remains the source format for manually maintained technical documentation.

#### User Documentation

Documents application functionality and workflows.

Content includes:

- Installation instructions.
- User guides.
- Feature descriptions.
- Operational procedures.
- Troubleshooting instructions.

#### Documentation Generation

Features:

- Build Markdown-based documentation.
- Generate HTML documentation.
- Generate PDF documentation when supported by the configured pipeline.
- Validate links and references.
- Display build errors and warnings.
- Publish documentation through the configured publishing workflow.

#### Tool Integration

Select one primary documentation generator according to the existing repository structure.

- MkDocs — preferred when the documentation is predominantly Markdown-based.
- Sphinx — introduced when API documentation requirements justify its additional capabilities.
- Mermaid and Graphviz — diagram generation and architectural representations.

The application should avoid maintaining parallel documentation pipelines without a demonstrated need.

Documentation source files remain maintained in the main repository. Generated documentation must not replace or overwrite their source files.

### 2.5 Build & Installer

Provides a centralized interface for building and distributing CranioZ.

#### Build Configuration

Features:

- Select build profiles.
- Configure application version.
- Configure application metadata and icon.
- Define included resources and dependencies.
- Configure output directories.
- Execute and monitor builds.

#### Executable Generation

Initial integration:

- PyInstaller.

Nuitka may be evaluated later if a specific compilation or distribution requirement justifies an alternative.

The build process must account for the application's runtime dependencies, Qt resources, VTK components, plugins, configuration files, and other required assets.

#### Installer Generation

For Windows distribution, the application may integrate:

- Inno Setup.
- NSIS.

The installer generator should be selected according to the project's distribution requirements.

Features:

- Generate application installers.
- Configure installation directory and application metadata.
- Include required runtime files.
- Configure shortcuts and application icons.
- Define installation and uninstallation behavior.
- Maintain build and installer history.

#### Build Validation

Validation is organized into three explicit levels:

**Level 1 — Artifact Integrity**

Automatic and always executed.

- Verify expected output files.
- Verify that required files are non-empty.
- Check artifact integrity using checksums.
- Record validation results.

**Level 2 — Application Smoke Test**

Automatic when the environment permits.

- Start the generated application in a clean subprocess.
- Apply a defined startup timeout.
- Capture startup errors and process exit status.
- Verify that the application starts successfully.

**Level 3 — Installation Validation**

Executed in a controlled environment, such as a virtual machine or disposable environment.

- Install the application.
- Verify installation behavior.
- Start the installed application.
- Verify required application resources.
- Uninstall the application.
- Check for unexpected residual files and configuration.

Build generation and installer creation must remain separate operations. The executable should pass the applicable validation before being packaged into an installer.

### 2.6 Architecture

Provides tools for inspecting the project's internal structure and architectural dependencies.

Features:

- Visualize module dependencies.
- Inspect import relationships.
- Identify circular dependencies.
- Verify architectural dependency rules.
- Display dependency relationships between architectural layers.

Potential integrations:

- Graphify — codebase relationship analysis.
- Graphviz — graph visualization.
- Import Linter — architectural dependency enforcement.

Architecture inspection must distinguish between visualization and enforceable architectural rules.

Graph visualization is supplementary. Import Linter remains responsible for enforcing explicitly defined dependency contracts.

### 2.7 Reports

Provides consolidated access to development operation results.

Features:

- Code verification reports.
- Test execution reports.
- Coverage reports.
- Documentation build reports.
- Build and installer reports.
- Execution history.
- Comparison of results between executions.

Reports must reference their corresponding execution records and generated artifacts.

The Reports area is independent of Architecture and aggregates results from all functional areas.

## 3. Shared Execution Infrastructure

All development operations must use a shared execution infrastructure.

The interface must not directly execute external tools or implement their operational logic.

### 3.1 Execution Engine

Responsible for:

- Starting external processes and internal tasks.
- Managing standard output and standard error.
- Reporting execution progress.
- Supporting cancellation when possible.
- Recording execution duration.
- Capturing exit codes.
- Reporting success, failure, and cancellation.
- Managing execution results.

Long-running operations must execute outside the UI thread.

Process cancellation must be documented per platform.

On Windows, cancellation must terminate the entire process tree rather than only the direct child process. The implementation may use a dedicated process-management dependency, such as `psutil`, when appropriate.

The application must explicitly handle cancellation failures and report processes that could not be terminated.

### 3.2 Tool Adapters

External tools should be integrated through dedicated adapters.

An adapter is responsible for:

- Resolving the executable or Python module.
- Preparing command-line arguments.
- Applying the appropriate working directory.
- Starting the operation through the Execution Engine.
- Interpreting the result.
- Returning structured execution information.

The application should reuse existing scripts and configurations whenever possible.

Adapters must not independently implement process management.

### 3.3 Execution Results

Operations should produce structured results containing, when applicable:

- Execution identifier — unique identifier used as the key for history and reports.
- Parent execution identifier — when the operation belongs to a larger workflow.
- Operation identifier.
- Operation type.
- Start and completion timestamps.
- Execution status.
- Exit code.
- Environment information, including Python interpreter, tool version, working directory, and project root.
- Generated artifact references.
- Relevant warnings and errors.

Execution information should be organized into three distinct categories:

**Execution Metadata**

Contains identifiers, timestamps, status, environment information, and artifact references.

**Execution Logs**

Contains standard output, standard error, and detailed operational logs.

Logs should be stored separately from execution metadata and referenced by the corresponding execution identifier.

**Execution Artifacts**

Contains generated reports, coverage files, documentation outputs, executables, installers, and other operation outputs.

The result model must be independent of the UI.

### 3.4 Execution History

Execution history must support:

- Persistent storage between application sessions.
- Retrieval by execution identifier.
- Filtering by operation type and status.
- Access to execution logs and artifacts.
- Comparison between previous executions.

History and artifact retention must follow a configurable policy to prevent unlimited storage growth.

## 4. Proposed Architecture

The Development Center should follow a modular Python architecture.

```text
tools/
└── development_center/
    ├── pyproject.toml
    └── src/
        └── development_center/
            ├── core/
            │   ├── execution/
            │   ├── persistence/
            │   ├── registry/
            │   ├── results/
            │   └── reporting/
            │
            ├── services/
            │   ├── code_extraction/
            │   ├── verification/
            │   ├── testing/
            │   ├── documentation/
            │   ├── build/
            │   ├── installer/
            │   └── architecture/
            │
            ├── adapters/
            │   ├── ruff/
            │   ├── mypy/
            │   ├── pytest/
            │   ├── coverage/
            │   ├── documentation/
            │   ├── pyinstaller/
            │   └── import_linter/
            │
            └── ui/
                ├── dashboard/
                ├── code_extraction/
                ├── verification/
                ├── documentation/
                ├── build/
                ├── architecture/
                └── reports/
```

This structure is a functional organization, not a requirement to create every package immediately. Components should be introduced as their corresponding features are implemented.

### 4.1 Architectural Principles

- Python-first implementation.
- PySide6 for the desktop interface.
- Separation between UI, services, adapters, and execution infrastructure.
- External tools remain independently executable.
- Reuse existing project scripts and configurations.
- Avoid duplicating functionality already provided by established tools.
- Keep the application independent of the CranioZ clinical runtime.
- Use typed interfaces and structured results.
- Keep operations testable and independently maintainable.

A complex plugin framework is not required initially. Tool registration should remain simple and explicit.

## 5. Configuration and Project Context

The Development Center must identify the CranioZ project root and use it as the working context for development operations.

Configuration is divided into two explicit scopes.

### 5.1 Project Configuration

Read from the project's existing configuration files, including:

- `pyproject.toml`.
- Pytest configuration.
- Ruff configuration.
- Mypy configuration.
- Documentation configuration.
- Other existing project-specific settings.

Project configuration must not be duplicated or independently overridden by the Development Center.

### 5.2 Application Configuration

Owned by the Development Center.

Includes:

- Project root selection.
- Extraction profiles.
- Build profiles.
- Installer configuration.
- Tool executable locations when necessary.
- Report and execution history locations.
- Retention policies.

### 5.3 Python Environment Resolution

The Python interpreter or virtual environment must be resolved using the following precedence:

1. Explicitly configured interpreter.
2. Project `.venv`.
3. Interpreter running the Development Center.

The interpreter actually used must be recorded in every execution result and displayed in the UI.

The application must not silently switch interpreters during an operation.

## 6. Implementation Strategy

Development should proceed incrementally, prioritizing reuse, operational reliability, and explicit completion criteria.

### Phase 0 — Foundation and Contract

- Inspect existing code extraction and packaging utilities.
- Identify their interfaces, configurations, dependencies, and current behavior.
- Identify existing development scripts and tool configurations.
- Define the `ExecutionResult` model as a typed structure independent of the UI.
- Define the persistence model for execution history and artifacts.
- Define environment resolution rules: project root, interpreter precedence, and working directory.
- Define a retention policy for execution history and artifacts.

**Completed when:** existing utilities have been inventoried, and a fake `ExecutionResult` can be serialized, persisted, and recovered from history in an automated test.

### Phase 1 — Execution Engine and Reference Adapter

- Implement the Execution Engine.
- Implement subprocess execution.
- Implement standard output and error capture.
- Implement process cancellation, including Windows process-tree handling.
- Implement exit code capture and structured status reporting.
- Implement the Ruff adapter as the reference integration.
- Implement a minimal UI with an execution trigger, output view, and history view.

**Completed when:** Ruff can be executed from the UI, its structured result is displayed and persisted across sessions, and the running operation can be cancelled.

### Phase 2 — Verification and Testing

- Integrate Mypy.
- Integrate Pytest.
- Integrate Coverage.py.
- Implement consolidated results.
- Implement structured presentation of test failures.

**Completed when:** every adapter has an automated test using a fake subprocess, and Pytest failures display parsed information rather than only raw terminal output.

### Phase 3 — Dashboard

- Implement the main application interface.
- Display execution history and project status aggregated from previous phases.
- Implement filtering and access to previous execution results.
- Ensure the dashboard does not execute operations on its own.

**Completed when:** the dashboard reflects real executions without triggering any operation by itself.

### Phase 4 — Code Extraction

- Inspect and integrate the existing code extraction utilities.
- Implement reusable TXT export profiles.
- Implement exclusion rules and output configuration.
- Implement sensitive-file protection.
- Preserve relative paths and source content.

**Completed when:** profiles can be saved and reused, sensitive files are excluded by default, and extraction is verified not to modify original source files.

### Phase 5 — Documentation

- Inspect the existing documentation structure.
- Select one primary documentation generator.
- Prefer MkDocs when the repository is predominantly Markdown-based.
- Introduce Sphinx when API documentation requirements justify it.
- Implement documentation generation.
- Implement link and reference validation.
- Display build errors and warnings.
- Add publishing workflows when required.

**Completed when:** documentation can be built from the UI, and errors are navigable and actionable without modifying source documentation.

### Phase 6 — Build (Executable Only)

- Integrate PyInstaller.
- Configure executable build profiles.
- Implement Level 1 artifact validation.
- Implement Level 2 application smoke testing when the environment permits.
- Record build metadata and available Git commit information.

**Completed when:** an executable is produced, passes Level 1 validation, and successfully starts in the configured smoke-test environment.

### Phase 7 — Installer

- Integrate the selected installer generator (Inno Setup or NSIS).
- Configure installation directory, metadata, shortcuts, and uninstallation behavior.
- Implement Level 3 installation validation in a controlled environment.
- Record installer history and generated artifacts.

**Completed when:** the installer is generated, installs the application, starts it, and uninstalls it without unexpected residual files or configuration in a controlled environment.

### Phase 8 — Architecture and Reports

- Integrate Import Linter as an enforceable architectural rule.
- Implement dependency inspection and visualization where useful.
- Integrate Graphify or Graphviz when justified.
- Implement consolidated verification, test, coverage, documentation, and build reports.
- Implement execution history comparison.

**Completed when:** Import Linter fails the verification workflow when an architectural contract is violated, and consolidated reports reference executions and artifacts by identifier.

### Phase 9 — Dogfooding and Hardening

- Use the Development Center as the primary tool for CranioZ development for an extended period.
- Add structured logging for the Development Center itself.
- Review execution reliability and artifact management.
- Fix friction points discovered during real use.
- Improve operational error handling.

**Completed when:** all development tasks covered by the Development Center can be performed through its interface without requiring manual terminal operations for those workflows.

## 7. Scope Boundaries

The Development Center is intended to centralize existing development workflows, not become a general-purpose software development environment.

The following principles define its boundaries:

- It does not replace an IDE such as PyCharm.
- It does not replace Git or version-control workflows.
- It does not reimplement Ruff, Mypy, Pytest, or other specialized tools.
- It does not require the CranioZ clinical application to be operational.
- It does not generate ZIP packages.
- It does not modify source files during extraction.
- It does not introduce a complex plugin ecosystem without a demonstrated need.
- It does not perform deployment to servers.
- It does not sign distributed binaries.
- It does not manage credentials.
- Publication tokens and secrets are provided by the environment and are never stored by the Development Center.

Its primary responsibility is to provide a consistent interface for executing, monitoring, and reporting development operations.

## 8. Risks and Mitigations

| Risk | Mitigation |
|---|---|
| PyInstaller packaging with Qt and VTK fails on a clean machine. | Level 1 validation runs automatically; Level 2 smoke testing verifies application startup; Level 3 validation is performed in a controlled environment. |
| Subprocess cancellation on Windows leaves orphaned processes. | Terminate the entire process tree and explicitly report cancellation failures. |
| Source extraction includes credentials or clinical data. | Apply default exclusion rules, sensitive-file detection, and explicit confirmation for exceptional inclusion. |
| Scope grows into a general-purpose IDE. | Enforce Section 7 at every phase review. |
| Execution history grows without limit. | Define a retention policy in Phase 0 for execution metadata, logs, and artifacts. |
| Duplicated configuration diverges from the project's real configuration. | Read project configuration from existing files only; do not duplicate linting, testing, or documentation rules. |
| A phase is considered complete without an automated criterion. | Every phase defines a completion criterion; no phase advances without it. |
| Tool versions drift and results become non-reproducible. | Record interpreter, tool version, working directory, project root, and available Git commit information in each execution result. |
| Documentation pipelines become unnecessarily complex. | Select one primary documentation generator and introduce additional tools only when justified. |
| Build results cannot be traced to their source state. | Associate builds with execution identifiers, build configuration, and available Git commit information. |

## 9. Expected Outcome

The CranioZ Development Center will provide a unified environment for the software development lifecycle.

It will allow developers to:

1. Extract and consolidate source code into `.txt` files.
2. Verify code quality and architectural constraints.
3. Execute automated tests and inspect coverage.
4. Generate and validate API, technical, and user documentation.
5. Build executable applications.
6. Generate and validate installers.
7. Inspect architecture and dependency relationships.
8. Review execution history and consolidated reports.

The result is a standalone development utility that simplifies maintenance and distribution of CranioZ while preserving the independence of its underlying tools and workflows.
