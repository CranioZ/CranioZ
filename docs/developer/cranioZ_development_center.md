# CranioZ Development Center

## 1. Overview

The **CranioZ Development Center** is an independent desktop application designed to centralize development and maintenance workflows for the CranioZ project.

It provides a unified interface for source code extraction, code verification, automated testing, architecture inspection, documentation generation, application builds, and installer creation.

The application integrates existing development tools and project scripts rather than replacing their underlying functionality.

### 1.1 Goals

- Centralize development workflows in a single application.
- Reuse existing code extraction and packaging utilities.
- Automate code verification and testing.
- Generate and validate project documentation.
- Build executable applications and installers.
- Provide consolidated reports and execution history.
- Reduce repetitive terminal operations.

### 1.2 Scope

The Development Center is a development utility, not a clinical CranioZ module.

It must operate independently of the CranioZ application runtime, allowing development and maintenance tasks to continue even when the main application cannot start.

## 2. Application Structure

The application is organized into six functional areas.

### 2.1 Dashboard

Provides an overview of the project's development status.

Features:

- Last verification results.
- Test execution status.
- Code quality and type-checking results.
- Test coverage.
- Documentation build status.
- Last successful application build.
- Recent execution history.

The dashboard presents information generated by the other application areas. It should not independently execute development operations.

### 2.2 Code Extraction

Provides tools for extracting and consolidating project source code.

Features:

- Select individual files or directories.
- Extract specific modules or architectural layers.
- Generate a consolidated `.txt` file.
- Save reusable selection profiles.
- Configure exclusion rules.
- Configure output filename and destination.

Supported selection profiles may include:

- Full Project.
- Core Architecture.
- Domain Layer.
- Application Layer.
- Infrastructure Layer.
- UI Layer.
- Specific Module.
- Documentation Only.

#### TXT Export

The generated text file should:

- Preserve the relative path of each source file.
- Include the original filename and extension.
- Separate files using clear delimiters.
- Optionally include a project directory index.
- Preserve the original source content.

Common exclusions include:

- `.venv/`
- `__pycache__/`
- `.git/`
- Build and distribution directories.
- Cache directories.
- Binary and generated files.

The extraction process must not modify the original project files.

**ZIP export and general-purpose archive generation are outside the scope of this application.**

### 2.3 Verification & Testing

Centralizes code quality checks, static analysis, and automated testing.

#### Code Verification

Integrate the project's existing tools:

- Ruff — linting and code formatting.
- Mypy — static type checking.
- Import Linter — architectural dependency contracts.
- Dependency auditing — identification of known vulnerable dependencies.

Verification operations should support diagnostic execution separately from operations that modify source files.

#### Testing

Integrate:

- Pytest — automated test execution.
- Coverage.py — test coverage measurement.

Features:

- Run the complete test suite.
- Run selected tests.
- Run tests by module or architectural layer.
- Display test failures and execution output.
- Display coverage results.
- Maintain execution history.

The application must use the project's existing test configuration.

### 2.4 Documentation

Provides tools for generating, validating, and publishing project documentation.

Features:

- Generate API documentation.
- Extract documentation from docstrings and type annotations.
- Build Markdown-based documentation.
- Generate HTML documentation.
- Generate PDF documentation when supported by the configured documentation pipeline.
- Validate documentation links and references.
- Display documentation build errors and warnings.
- Publish documentation through the configured publishing workflow.

Potential integrations:

- Sphinx — API documentation and technical documentation.
- MkDocs — Markdown-based documentation.
- Mermaid and Graphviz — diagrams and architectural representations.

The documentation source files remain maintained in the main repository. Generated documentation must not replace or overwrite its source files.

### 2.5 Build & Installer

Provides a centralized interface for building and distributing CranioZ.

#### Build Configuration

Features:

- Select build profiles.
- Configure application version.
- Configure application metadata and icon.
- Define included resources and dependencies.
- Configure output directories.
- Execute and monitor builds.

#### Executable Generation

Potential integrations:

- PyInstaller.
- Nuitka, when an alternative compilation workflow is required.

The build process must account for the application's runtime dependencies, Qt resources, VTK components, plugins, configuration files, and other required assets.

#### Installer Generation

For Windows distribution, potential integrations include:

- Inno Setup.
- NSIS.

Features:

- Generate application installers.
- Configure installation directory and application metadata.
- Include required runtime files.
- Configure shortcuts and application icons.
- Define installation and uninstallation behavior.
- Maintain build and installer history.

#### Build Validation

Where feasible, validate generated artifacts through automated checks:

- Verify expected output files.
- Check package integrity.
- Test application startup.
- Test installation and uninstallation.
- Record build errors and warnings.

Build generation and installer creation must be separate operations so that an executable can be tested before being packaged into an installer.

### 2.6 Architecture & Reports

Provides tools for inspecting the project's internal structure and consolidating development results.

#### Architecture Inspection

Features:

- Visualize module dependencies.
- Inspect import relationships.
- Identify circular dependencies.
- Verify architectural dependency rules.
- Display dependency relationships between architectural layers.

Potential integrations:

- Graphify — codebase relationship analysis.
- Graphviz — graph visualization.
- Import Linter — architectural dependency enforcement.

Architecture inspection must distinguish between visualization and enforceable architectural rules.

#### Reports

Features:

- Consolidated verification reports.
- Test execution reports.
- Coverage reports.
- Documentation build reports.
- Build and installer reports.
- Execution history.
- Comparison of results between executions.

Reports should retain references to the corresponding execution and its generated artifacts.

## 3. Shared Execution Infrastructure

All development operations must use a shared execution infrastructure.

The interface must not directly execute external tools or implement their operational logic.

### 3.1 Execution Engine

Responsible for:

- Starting external processes and internal tasks.
- Managing standard output and standard error.
- Reporting execution progress.
- Supporting cancellation when possible.
- Recording execution duration.
- Capturing exit codes.
- Reporting success, failure, and cancellation.
- Managing execution results.

Long-running operations must execute outside the UI thread.

### 3.2 Tool Adapters

External tools should be integrated through dedicated adapters.

An adapter is responsible for:

- Resolving the executable or Python module.
- Preparing command-line arguments.
- Applying the appropriate working directory.
- Starting the operation through the Execution Engine.
- Interpreting the result.
- Returning structured execution information.

The application should reuse existing scripts and configurations whenever possible.

### 3.3 Execution Results

Operations should produce structured results containing, when applicable:

- Operation identifier.
- Operation type.
- Start and completion timestamps.
- Execution status.
- Exit code.
- Standard output.
- Standard error.
- Generated artifact references.
- Relevant warnings and errors.

The result model should be independent of the UI.

## 4. Proposed Architecture

The Development Center should follow a modular Python architecture.

```text
tools/
└── development_center/
    ├── pyproject.toml
    └── src/
        └── development_center/
            ├── core/
            │   ├── execution/
            │   ├── registry/
            │   ├── results/
            │   └── reporting/
            │
            ├── services/
            │   ├── code_extraction/
            │   ├── verification/
            │   ├── testing/
            │   ├── documentation/
            │   ├── build/
            │   ├── installer/
            │   └── architecture/
            │
            ├── adapters/
            │   ├── ruff/
            │   ├── mypy/
            │   ├── pytest/
            │   ├── coverage/
            │   ├── sphinx/
            │   ├── mkdocs/
            │   ├── pyinstaller/
            │   └── import_linter/
            │
            └── ui/
                ├── dashboard/
                ├── code_extraction/
                ├── verification/
                ├── documentation/
                ├── build/
                ├── architecture/
                └── reports/
```

This structure is a functional organization, not a requirement to create every package immediately. Components should be introduced as their corresponding features are implemented.

### 4.1 Architectural Principles

- Python-first implementation.
- PySide6 for the desktop interface.
- Separation between UI, services, adapters, and execution infrastructure.
- External tools remain independently executable.
- Reuse existing project scripts and configurations.
- Avoid duplicating functionality already provided by established tools.
- Keep the application independent of the CranioZ clinical runtime.
- Use typed interfaces and structured results.
- Keep operations testable and independently maintainable.

A complex plugin framework is not required initially. Tool registration should remain simple and explicit.

## 5. Configuration and Project Context

The Development Center must identify the CranioZ project root and use it as the working context for development operations.

Configuration should support:

- Project root directory.
- Python interpreter or virtual environment.
- Tool executable locations when necessary.
- Documentation source and output directories.
- Build profiles.
- Installer configuration.
- Code extraction profiles.
- Report and execution history locations.

The application should reuse the project's existing `pyproject.toml`, test configuration, linting rules, and other configuration files rather than maintaining duplicated settings.

## 6. Implementation Strategy

Development should proceed incrementally, prioritizing reuse and operational reliability.

### Phase 1 — Existing Utilities

- Inspect existing code extraction and packaging utilities.
- Identify their interfaces, configurations, and dependencies.
- Integrate them into the new application.
- Implement reusable TXT export profiles.

### Phase 2 — Execution Infrastructure

- Implement the Execution Engine.
- Implement process output capture.
- Implement task status and cancellation.
- Implement structured execution results.

### Phase 3 — Verification & Testing

- Integrate Ruff.
- Integrate Mypy.
- Integrate Pytest.
- Add Coverage.py.
- Implement consolidated results.

### Phase 4 — Dashboard

- Implement the main application interface.
- Display execution history and project status.
- Integrate the existing functional areas.

### Phase 5 — Documentation

- Integrate Sphinx and/or MkDocs according to the repository's documentation structure.
- Implement documentation generation.
- Implement build validation.
- Add publishing workflows when required.

### Phase 6 — Build & Installer

- Integrate PyInstaller.
- Configure executable build profiles.
- Integrate the selected installer generator.
- Implement artifact validation and build history.

### Phase 7 — Architecture & Reports

- Integrate Import Linter.
- Add dependency inspection and visualization.
- Integrate Graphify where useful.
- Implement consolidated reports.

## 7. Scope Boundaries

The Development Center is intended to centralize existing development workflows, not become a general-purpose software development environment.

The following principles define its boundaries:

- It does not replace an IDE such as PyCharm.
- It does not replace Git or version-control workflows.
- It does not reimplement Ruff, Mypy, Pytest, or other specialized tools.
- It does not require the CranioZ clinical application to be operational.
- It does not generate ZIP packages.
- It does not modify source files during extraction.
- It does not introduce a complex plugin ecosystem without a demonstrated need.

Its primary responsibility is to provide a consistent interface for executing, monitoring, and reporting development operations.

---

## 8. Expected Outcome

The CranioZ Development Center will provide a unified environment for the software development lifecycle.

It will allow developers to:

1. Extract and consolidate source code into `.txt` files.
2. Verify code quality and architectural constraints.
3. Execute automated tests and inspect coverage.
4. Generate and validate documentation.
5. Build executable applications.
6. Generate and validate installers.
7. Inspect architecture and dependency relationships.
8. Review execution history and consolidated reports.

The result is a standalone development utility that simplifies maintenance and distribution of CranioZ while preserving the independence of its underlying tools and workflows.
